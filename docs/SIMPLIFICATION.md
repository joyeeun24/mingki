# 단순화 계획 (초안)

팀 결정: 개발자 · 담당자 역할 구분을 없애고, **규정(법령) 개정을 읽어 바뀐 점을 찾고, 업데이트해야 할 상품 정보를 제안**하는 제품으로 줄인다.
이 문서는 단순화 방향과, 그렇게 해도 Capstone 평가표를 지키는지 확인한 결과다. 2026-10-20 기준 main(#11 MCP 머지)과 `feature/agent`(ed4034b)를 보고 썼다.

## 2. 단순화 방향

| | 지금 | 단순화 후 |
|---|---|---|
| 하는 일 | 규정 → 요건 → 코드 위치 → 코드 수정안 → 검증 → Draft PR · 티켓 | 규정 → 바뀐 조항 → 영향 받는 상품 규칙 → **상품 업데이트 제안** → 확인 → **상품 규칙 새 버전 등록** |
| 사람 | 담당자 결재 + 개발자 승인 (역할 2개, 2번) | 역할 구분 없이 **1번 확인** |
| 결과물 | Draft PR, 작업 티켓 | 상품 업데이트 제안서 + 반영된 상품 규칙 (시행일 버전) |
| 빠지는 것 | | 코드 검색 · 코드 수정안 · 테스트 생성 · 샌드박스 검증 · PR · 티켓, code-mcp |

결과 예시 (정답지 `eval/answer_key.md` 2절 기준):

| 상품 | 규칙 | 지금 | 제안 | 근거 |
|---|---|---|---|---|
| P001 직장인 신용대출 | `DSR_LIMIT` (R001) | 0.40 | 0.35 | 제8조, 2026-12-01부터 |
| P002 시니어 든든대출 | `DSR_LIMIT` (R011) | 0.40 | 0.35 | 제8조 |
| P002 시니어 든든대출 | `ELIGIBLE_MIN_AGE` (R010) | 65 | 60 | 제15조 |
| 대상 아님 | `MORTGAGE_LTV_LIMIT`, `INCOME_EST_RETIREMENT_AGE`, P003 `DSR_LIMIT 0.35`, `SENIOR_RATE_DISCOUNT` 등 | | 그대로 | 같은 숫자 · 다른 의미, 이미 신 기준 충족, 우대 폭 변경 없음 |

반영 방식: 기존 행은 고치지 않고 `effective_to = 2026-11-30`으로 닫고, `effective_from = 2026-12-01` 새 행을 추가한다 (경과조치: 시행일 전 신청분은 종전 값).

## 3. 평가표를 지키는 단순화 흐름

그냥 덜어내면 평가 항목이 빠진다(4절). 아래처럼 **흐름의 뼈대(분기 · 반복 · 사람 확인 · 쓰기 도구 · 대기열)는 남기고 내용만 상품 규칙으로 바꾼다.**

```
업로드 ─▶ 바뀐 조항 추출 ─(실질 변경 0건)─▶ 종료(NO_CHANGE)
            │ rag-mcp: 조항 비교 · 검색
            ▼
        영향 상품 규칙 찾기          business-mcp: 상품 · 규칙 · 계약 조회
            ▼
        제안 작성 (규칙별 지금 값 → 제안 값, 시행일)
            ▼
        제안 검증 (코드) ─(실패, 재시도 남음)─▶ 제안 작성   ← 반복
            ▼
        사람 확인 [interrupt] ─(거절)─▶ 종료(REJECTED)      ← 상태 저장 · 재개
            │ 제안마다 반영 / 제외
            ▼
        상품 규칙 새 버전 등록     business-mcp 변경 도구 → 승인 검증 → 대기열(재시도 · DLQ)
            ▼
        리포트 ─▶ 완료(DONE)
```

| 단계 | 백엔드 상태 (지금 있는 것 재사용) | 뜻 |
|---|---|---|
| 바뀐 조항 추출 | `EXTRACTING` | 그대로 |
| 영향 찾기 | `LOCATING` | 코드 대신 상품 규칙 |
| 제안 작성 | `DESIGNING` | 코드 수정안 대신 상품 규칙 제안 |
| 제안 검증 | `VERIFYING` | 샌드박스 대신 규칙 검사 |
| 사람 확인 | `WAITING_REVIEW` | 역할 없이 로그인한 사용자 |
| 반영 | `PUBLISHING` | PR · 티켓 대신 상품 규칙 새 버전 |
| 종료 | `DONE` · `NO_CHANGE` · `REJECTED` · `FAILED` | 그대로 |

`WAITING_REQUIREMENT_APPROVAL`, `HELD`(요건 결재)만 쓰지 않는다. 상태 이름을 대부분 그대로 쓸 수 있어서 백엔드 · 프론트 변경이 작다.

제안 검증(코드로 판단, LLM 아님):
- 제안 값이 바뀐 조항의 숫자와 같은가 (예: 제8조 35% → 0.35)
- 함정을 고치지 않았는가 (같은 값이라도 다른 기준인 규칙)
- 단위 · 시행일이 맞는가 (`effective_from` = 시행일, 종전 행 `effective_to` = 시행일 전날)
- 이미 신 기준을 충족하는 규칙에 불필요한 제안을 하지 않았는가

## 4. 평가표 대조

✅ 지금 계획으로 충족 · ⚠️ 조건을 지켜야 충족 · ❌ 단순화와 무관하게 아직 비어 있음

| 항목 | 그냥 덜어내면 | 3절 흐름으로 하면 | 지켜야 할 조건 |
|---|---|---|---|
| Biz. 아이템 (10) | ✅ | ✅ | 은행 준법 · 상품기획 대상 B2B RegTech. 오히려 사용자가 분명해짐 |
| 아키텍처 설계 (10) | ✅ | ⚠️ | **ISO/IEC 25010 품질 특성별 설계 근거 문서가 없음** (단순화와 무관). 보안 · 신뢰성 · 유지보수성 · 사용성 대응을 표로 정리해야 함 |
| AI Agent 설계 (15) | ❌ 반복이 사라짐 | ✅ | 분기(변경 0건 · 거절)와 **반복(제안 검증 → 재작성)** 유지 |
| AI Agent 구현 (15) | ⚠️ | ⚠️ | 모델의 도구 선택 + 근거(이미 있음). **상태 저장 · 재개**: 사람 확인 1번 + DB 체크포인터. **진행 이벤트**: Agent ↔ Spring HTTP 연결이 아직 없음 (단순화와 무관) |
| MCP 설계 · 구현 (20) | ❌ 변경 도구가 사라짐 | ✅ | **business-mcp 변경 도구**: 티켓 생성 대신 "상품 규칙 새 버전 등록". **rag-mcp**: 지금 키워드 검색이라 Vector DB 의미 검색으로 교체 필요 (단순화와 무관), 업로드 원문 등록 도구가 있으면 업로드 파일 문제도 해결 |
| Harness (20) | ⚠️ 사람 개입 · 쓰기 통제가 줄어듦 | ✅ | interrupt · 재개, 체크포인터, 노드별 도구 권한, 쓰기 도구의 승인 ID 서버 검증 + 멱등키, 진행 이벤트, 평가 스크립트 |
| 인증 (10) | ✅ | ✅ | 역할은 없애도 **로그인(JWT)은 유지** |
| 가산점 대기열 (10) | ❌ 대기열 작업이 모두 사라짐 | ✅ | 지금 작업 종류(패치 검증 · PR · 티켓)가 전부 빠지므로, **"상품 규칙 반영"을 대기열 작업으로** 처리하고 재시도 · DLQ 유지 |

결론: **단순화 자체는 평가표에 위배되지 않는다. 단, "그냥 덜어내기"로 하면 AI Agent 설계 · MCP · 대기열에서 최대 45점이 위험하다.** 3절처럼 뼈대를 남기고 내용만 상품 규칙으로 바꾸면 모든 항목을 지킬 수 있다.
